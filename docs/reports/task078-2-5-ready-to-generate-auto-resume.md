## Root Cause And Evidence

The user supplied Production readiness evidence for the selected 24P case: `totalSource=28`, `ready=24`, `pending=0`, `failed=4`, `eligibleReady=24`, `requiredEligible=12`. Under the Task078.2.4 capacity contract this is generation-ready.

In the client, generation was triggered inline inside the readiness polling callback. Readiness was also stored in React state, but there was no independent effect observing the `(intent, readiness)` pair. That left the transition coupled to the lifetime and captured intent of one asynchronous poll, including intent restoration/rerender timing. A ready response that was not consumed by that callback had no explicit state observer to restart the transition.

The shared Production page was inspected read-only during this task. Its current snapshot showed the older simple page-count selector, a “写真を確認しています” state, and an available “準備してアルバムを作る” button; it did not show an active locked intent or the reported 24P state. No button was clicked. This snapshot does not confirm that the supplied ready response and active intent belong to the same Production page/deployment, so Production completion is not claimed.

## Fix And State Transition

- Added `shouldAutoResumeAlbum`, requiring an intent, valid/unexpired intent state, readiness `ready`, `eligibleReady >= required`, and no running generation.
- Added an independent ready-state observer keyed by intent, readiness, and current setup. It runs after the ready response is committed to state, covering ready-at-intent-creation and restored-intent cases instead of relying only on the poll callback.
- Immediately before dispatch, the client revalidates the route/owner-bound intent and matches pet IDs, period, and page count against the current setup. Stale conditions lead to actionable recovery rather than submission.
- The existing in-memory lock is set before dispatch. Strict Mode reruns and auto/manual races are suppressed by the same lock; the server continues to bind the album primary key to the intent UUID and handle unique conflicts idempotently.
- A ready intent immediately renders the existing “アルバムを作っています” screen while the observer dispatches, without exposing a long-lived technical ready state.
- Reloaded preparing/generating intents are validated and rechecked. A ready valid intent resubmits the same ID; existing completed drafts return their existing Preview, and in-progress records retain bounded same-intent retry.
- Successful creation clears session intent and uses the existing Preview URL (`?view=preview`), never the Editor.

## Structured Logging

Client and server emit `albumAutoResume` records with `intentPresent`, `readinessStatus`, `eligibleReady`, `requiredEligible`, `autoResumeTriggered`, `generationStarted`, `generationCompleted`, and `duplicateSuppressed`. The logger schema contains no photo ID, album ID, pet ID, user ID, or other PII. The server records the capacity gate, existing-completed recovery, in-progress/unique-conflict suppression, and generation completion.
